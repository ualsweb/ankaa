## Known gaps
- Live SBE ingestion is implemented but unverified against the real endpoint (needs a free Binance API key).
- Replays of captures recorded without `--snapshots` start books cold; the bundled 20 s sample is such a capture.
- No benchmark result yet: the Axion comparison is one 4-vCPU VM, one hour of data, one day, competitors at stock settings; a publishable comparison needs captures of hours to days, a larger instance, repeated runs and tuned competitors. QEMU runs are functional only; laptop figures are development signals.
- The operators written on 2026-11-10 and 11 (`DenseAggExec`, block pre-aggregates, in-place table functions, `rolling()` and its continuous form, incremental snapshots, ordered and reverse scans, exact time filters, the plan cache, `EagerAggregation`, `OrderedMergeExec`) are covered by differential and property tests and by the comparison's verification, and by nothing else yet: no soak has finished on them and no external user has run them. `ANKAA_DENSE_AGGREGATION=off` turns the aggregation operator off.
- Still on DataFusion's general operators: `GROUP BY` on a wide or computed key, `date_bin` with months or an explicit origin, general joins and sorts, aggregates of computed expressions. The plan cache only helps statements whose text repeats exactly and that call no function of the clock; caching plans across changing literals (parameterised plans) was evaluated and not built: planning is 0.1–0.3 ms, and substituting values into an optimised plan would lose the exact time filters. A SQL-free API for fixed questions (latest price, last N trades) was also left out: with the plan cache and reverse scans those answer in 0.1–0.3 ms through SQL.
- Replication is asynchronous with manual failover: a quorum-replicated log was evaluated (durable write 0.87 ms on the VM disk, 0.09 ms network round trip between two VMs) and left for later, because queries do not wait for durability and it is an availability feature, not a latency one.
- Arm build flags were measured on Neoverse V2 and are not used: inlined LSE atomics changed nothing; `-C target-cpu=neoverse-v2` gained about 1 % on ingest and up to 7 % on one query, not enough to ship a binary that only runs on that CPU generation.
- SVE2 is slower than NEON at 128-bit vectors (every mainstream cloud Arm CPU today) for all kernels but 64-bit integer min/max; the SVE2 count kernels still use one accumulator. In the second comparison run QuestDB once returned a `sum` that was off by 12 × 2^32; it never reproduced and is unexplained.
- Recovery speed (F-19) is measured on the laptop only (see `docs/benchmarks/`); the 10 GB / 60 s target needs a server-class NVMe run. Start-up also rebuilds continuous queries by reading their input tables once per query: unmeasured on large histories.
- Delivery guarantees: file and Kafka sources are at least once (a crash repeats about one second of messages; the per-partition ordering rule rejects repeated older rows but not a repeat of the newest timestamp); NATS core is at most once. No exactly-once, no Kafka consumer groups, no SASL/TLS options for Kafka, no NATS credentials files.
- Ingest is bounded by what the WAL volume makes durable: a real-time feed that outruns the disk drops frames at the source channel (counted). A frame the log does not take within 2 s (stalled or failing disk) is dropped, not ingested (`ankaa_wal_dropped_total`); if it was a message of a user source the server stops (exit code non-zero, systemd restarts it) so that file and Kafka sources read it again. NATS messages lost that way are lost.
- With synchronised order books the WAL is kept back to the last feed connection before the checkpoint; when it outgrows `storage.wal_budget_mib` the books are re-based on fresh REST snapshots (at most every 10 minutes), which gives the log a new starting point at the price of a short gap in `quotes` while the snapshots arrive. Recovery replays the log from that point. Books run with `feed.depth_snapshots = false` are not replay-exact: `quotes` regenerated after a crash can differ from the originals.
- A WAL record that straddles a chunk boundary and contained a row the table rejected can have one row applied twice on crash recovery (never lost).
- Dictionary lookups use FNV-1a, which is not collision-resistant: a hostile producer can slow ingest of its own table (bounded by `max_dict_entries`).
- No cap on the number of Flight connections (each is limited to 64 concurrent calls; queries are capped globally).
- Replication is asynchronous with manual failover; there is no fencing of an old primary (the WAL `epoch` field is constant) and no automatic re-seed.
- Keyed ASOF continuous queries are limited to the market tables (user tables keep one dictionary each). Continuous queries drop late rows (no retraction).
- User tables can gain nullable columns at the end (or make a column nullable) with their history kept; any other column change stops the start with the reason (restore the definition or move the segments away).
- The `file://` capture feed re-serves its captures on every start: do not combine it with `storage.wal_dir` outside demos.
- Postgres wire: no TLS of its own and no statement timeout (the query memory pool applies); trusted tools only. `/metrics` is plaintext.
- Replay inputs are operator-supplied and partly trusted: WAL segments are read whole into memory at recovery (bounded by the 256 MiB segment size), CSV and Parquet files are read as they are.
- Not yet fuzzed: CSV/Parquet replay sources, segment metadata, the `/metrics` request parser; `capture_decode`/`wal_replay` are CRC-gated (structure-aware variants planned).
- `asof_join`/`ohlcv`/`percentiles` table functions collect both inputs in memory (bounded by the query memory pool, not streaming yet); Flight is plain Flight (SQL in descriptor/ticket), not the Flight SQL extension, so ADBC drivers need that first.
- MQTT ingest costs about 10 µs of server CPU per message on Axion, three quarters of it in the MQTT client (rumqttc writes every acknowledgement on its own); the engine's share is about 2.5 µs. Batching readings per message (`rows`, Sparkplug) brings it to about 1.1–1.3 µs per reading.
- `ankaa-wire` has no AF_XDP path and no bare-metal numbers.
- Segments carry no per-file checksum beyond the Vortex layout (metadata row count is checked).

## Facts worth keeping
- `libc` does not export `HWCAP2_SVE2`; it is bit 1 of `AT_HWCAP2` (kernel UAPI).
- Disassemblers print SVE branch aliases as flags (`b.first` = `b.mi`, `b.none` = `b.eq`); the branchless gate checks the predecessor instruction.
- dm-flakey has no message interface and `drop_writes` makes writes *succeed* without reaching the device: freeze the writer before the table reload or a rig acknowledges phantom commits.
- Binance diff-depth messages must be applied atomically before sampling top of book.
- Apple M4 exposes SME2 (512-bit streaming SVE) but no SVE outside streaming mode; build with `+sme2` and without base SVE or the compiler emits `addvl` that faults.

**Function-level profile and what it changed (2026-11-11).** Compaction merges chunks below half a chunk (`SMALL_CHUNK_ROWS`), runs of ≥ 4 or runs that reach half a chunk. `scripts/profile-telemetry.sh` (+ `bench/telemetry/loop_query.py`): perf cpu-clock profile of ankaad per phase (load, tiering, restart) and per statement, on a loaded and on a restarted server; micro level: `bench/benches/hot_paths.rs` (55 functions). Findings on c4a-standard-4 and the changes: (1) the hot-memory bound left 16,937 chunks of ~1,500 rows for 1,000 hosts → **compaction** (`tiering.rs`: `compact_small_chunks`, `small_run`, `run_job` with `Merge`, `install_merged`; `ankaa-store`: `Chunk::merged`, `Partition::replace_sealed_run`/`fresh_chunk_id`, `ChunkMeta::replaces`; `restore` deletes segments a merged one replaces); (2) pruning asked every chunk in turn (23 % of a single-device query) → `provider.rs::PruneIndex` (flat arrays per chunk list, id ranges per column on first use), also used by `latest`; (3) `Table::tier_stats` three times per tick (11.6 % while compressing) → `Tiering::tier_totals`; (4) `LIKE` compiled per batch (490 ms) → `ChunkTable::pred_over_names` (any predicate on one name column evaluated over the dictionary, then by id); (5) every table re-snapshotted each tick → `Partition::version`/`Table::version`, swap only on change (`serve.rs` `published_versions`); (6) cold reads paid file read + footer parse per call, and after a restart (everything cold) large scans were 2.5–5× slower than on the server that loaded the data → segment cache (`ankaa-tier`: `SegmentCache`, `Opened`: the file plus its columns as stored, loaded at first use and sliced like a warm chunk's; it also gets the unused warm budget); (7) time-bucket grouping per row (17–25 % of bucketed group-bys) → `dense_agg.rs::groups_by_bucket_runs`. - **Launch-readiness pass (2026-11-10):** whole-project review, fixes, and a second independent QA + security review.
  - *Durability and restarts:* user-table dictionaries persisted next to the segments (`dictionaries.json`, before any segment that uses their ids); stable source ids and durable read positions (`sources.json`): file sources resume at the saved byte offset, Kafka sources at saved offsets (at least once; verified against Kafka 3.9 across a clean stop and a SIGKILL); continuous-query tables are derived state, rebuilt at start from the input tables in timestamp order (same results before and after a restart or crash; end-to-end test with five restarts); orderly shutdown also on error exits; WAL handle commits on drop.

  - *Supply chain:* GitHub Actions pinned to commit SHAs with read-only default permissions; `cargo deny` on all four lockfiles; fuzz and bench crates built in CI (a fuzz target that no longer compiled was found this way); new fuzz target `generic_map`, `wal_replay` also drives the tail reader; criterion groups `generic_ingest`, `continuous_100k`, `wal_tail`.
  - *Second review round (three independent reviewers, findings fixed the same day):*
    - Ingest waits for the WAL instead of ingesting frames it could not log (the first-light recovery check had shown a quarter of the frames of a fast replay missing after a crash); commits batch adaptively (10 ms, or 256 KiB with an empty queue, or 8 MiB) and are retried without ever discarding the buffer; a failed commit rolls the segment back.
    - LSNs are never reused: the log restarts above every LSN that segments and saved source positions refer to, replay accepts the resulting jump at a segment boundary, and followers are told to re-seed across it. Rows of a partition created by the current record carry its LSN (the table, not each partition, holds the current LSN, which also makes it independent of the partition count).
    - Order-book rows are replayable after truncation: with synchronised books the log is kept back to the last feed connection at or before the checkpoint. A WAL budget (`storage.wal_budget_mib`) seals and persists the partitions that hold the log back.
    - Segments that cannot be read or have another column set stop the start instead of being skipped and later overwritten.
    - Kafka: partitions are merged by record timestamp (a multi-partition topic no longer has rows rejected as out of order), partitions added later are picked up, fetches time out; file and Kafka sources report their position on shutdown (a clean stop repeats nothing); the log records source ids so standbys and recovery bind user frames correctly.
    - Rejected messages no longer add dictionary values; chunk columns are allocated as data arrives (a key costs bytes, not half a megabyte); default dictionary cap 100,000.
    - Security: table functions (`ohlcv`, `asof_join`, `percentiles`) no longer run at plan time: they execute inside the query deadline, on the blocking pool, charged to the memory pool; query spill to disk disabled; a cap on concurrent queries; `SET timezone` over the Postgres protocol no longer reaches the shared session and the gate fails closed; a Flight listener beyond loopback needs TLS (or an explicit opt-out) and a token of at least 16 characters; URLs are logged without credentials; workflows drop checkout credentials; cargo-deny covers all five lockfiles.
    - Continuous queries: rebuild goes partition by partition when the key is the partition column (one decoded chunk per input in memory), ASOF counts left rows it cannot join, live tables have the same columns as closed ones and are exchanged without leaving the catalog.
  - *Verification round on those fixes (one more independent reviewer):* a standby no longer applies the LSN floor (it would have skipped records after losing its log); a checkpoint owed after a WAL-relief persist is handed out when the interval allows instead of being lost; `BEGIN`/`COMMIT`/`ROLLBACK`, `SET TRANSACTION`, `SET NAMES`, `DISCARD ALL` and `DEALLOCATE` are accepted over the Postgres protocol (drivers and ORMs wrap every query in them); the shutdown drain is bounded; when the WAL outgrows its budget because the order books depend on an old connection, the books are re-based on fresh snapshots (also when a snapshot or connect frame could not be logged); a user-source message the WAL cannot take stops the server so the source re-reads it after the restart; table functions compute nothing at physical planning either (`EXPLAIN`); deliberate jumps in WAL numbering carry a marker so a missing segment file is still reported.
  - *First light on Google Axion (2026-11-10):* the SVE2 kernels and the whole test suite pass on Neoverse V2 silicon, crash recovery is exact. A preliminary comparison with QuestDB, ClickHouse and DuckDB on the same VM (one hour of live Binance data, 12 symbols, every result verified against DuckDB, eight runs) found twelve problems in our own code and harness, all fixed the same day; the largest was that queries never reached the SIMD kernels. What came out of it: `DenseAggExec` (hash-free aggregation over dictionary ids, flag bytes and time buckets, answering from chunk statistics where it can), per-block pre-aggregates in chunks and segments, table functions that work on scan batches in place, `rolling()` windows, scan statistics for the planner, incremental live snapshots, per-kernel choice between NEON and SVE2 (SVE2 wins for 64-bit integer min/max at 128 bits), mimalloc as the server's allocator, one Flight call per query, exact time filters, time-ordered and reverse scans ("latest N rows" without reading the table), a `vwap()` aggregate, a plan cache, aggregation before joins, an own merge for sorted partitions and `rolling` continuous queries. In the tenth and last run ANKAA was ahead of the three engines on all seventeen queries. Note and raw results: `docs/benchmarks/2026-11-10-axion-first-light.md`, `bench/compare/results/`.
  - *Measurements (laptop, development signals):* `docs/benchmarks/2026-11-10-launch-readiness-signals.md`.
  - *Launch assets:* `docs/launch-checklist.md`, `scripts/first-light.sh` (system facts, build, native tests incl. SVE2, criterion, replay, crash recovery), `scripts/soak.sh` (scrapes `/metrics`, fails on gaps, drops, WAL errors or memory growth).

- **Flight SQL (2026-11-11):** the Flight port also answers the Flight SQL extension, read-only, for ADBC drivers, the Flight SQL JDBC driver and `FlightSqlServiceClient`. The existing `FlightService` looks for the Flight SQL envelope (a protobuf `Any` with an `arrow.flight.protocol.sql` type URL) in descriptors, tickets and action bodies and hands it to `ankaa-flight::flight_sql`; anything else is plain Flight as before (arrow-flight's own `FlightSqlService` was not used: its blanket `FlightService` implementation decodes every descriptor as `Any` before its fallback hooks run and has no `ListFlights` or `GetSchema`).
  - *Supported:* `CommandStatementQuery` (`GetFlightInfo`, `GetSchema`, `DoGet`); prepared statements without parameters (`CreatePreparedStatement`, `CommandPreparedStatementQuery`, `ClosePreparedStatement`); `CommandGetSqlInfo` (name, version, Arrow version, read-only, no transactions, no DDL, no cancel, no bulk ingest, identifier case and quote), `CommandGetCatalogs`, `CommandGetDbSchemas`, `CommandGetTables` with and without table schemas, `CommandGetTableTypes`; `Handshake` with the token as a bearer header or as the password of Basic authentication (padded or not), answered with `authorization: Bearer <token>`.
  - *How:* statement tickets and prepared-statement handles are the SQL text, so the server keeps nothing per client, and every statement is planned and executed by the functions plain Flight uses: the same read-only check, query timeout, cap on concurrent queries, memory pool and plan cache. Metadata is read from the catalog inside the query timeout, without a query slot, like `ListFlights`.
  - *Refused with a status:* `CommandStatementUpdate`, `CommandPreparedStatementUpdate` and `CommandStatementIngest` (read-only); statement parameters, at prepare, at `GetFlightInfo` and when a client binds them with `DoPut`; transactions and savepoints; Substrait plans; `CancelQuery`; `CommandGetPrimaryKeys`, `CommandGetExportedKeys`, `CommandGetImportedKeys`, `CommandGetCrossReference`, `CommandGetXdbcTypeInfo`.
  - *Verified:* 16 tests with `FlightSqlServiceClient` against an in-process server (`crates/ankaa-flight/tests/flight_sql.rs`): queries, prepared statements, metadata, the handshake, missing and wrong tokens on every call, refused writes and parameters, malformed envelopes and 200 seeds of random bytes, the query timeout, the query cap and the memory pool on this path. `adbc_driver_flightsql` 1.13 was run by hand against `ankaad serve` with `examples/python/flight_sql_adbc.py` (bearer header, user name and password, queries, `GetInfo`, `GetObjects`, table schema, refusals); that script is not in CI.

## Known gaps
- Live SBE ingestion is implemented but unverified against the real endpoint (needs a free Binance API key).
- Replays of captures recorded without `--snapshots` start books cold; the bundled 20 s sample is such a capture.
- No benchmark result yet: the Axion comparison is one 4-vCPU VM, one hour of data, one day, competitors at stock settings; a publishable comparison needs captures of hours to days, a larger instance, repeated runs and tuned competitors. QEMU runs are functional only; laptop figures are development signals.
- The operators written on 2026-11-10 and 11 (`DenseAggExec`, block pre-aggregates, in-place table functions, `rolling()` and its continuous form, incremental snapshots, ordered and reverse scans, exact time filters, the plan cache, `EagerAggregation`, `OrderedMergeExec`) are covered by differential and property tests and by the comparison's verification, and by nothing else yet: no soak has finished on them and no external user has run them. `ANKAA_DENSE_AGGREGATION=off` turns the aggregation operator off.
- Still on DataFusion's general operators: `GROUP BY` on a wide or computed key, `date_bin` with months or an explicit origin, general joins and sorts, aggregates of computed expressions. The plan cache only helps statements whose text repeats exactly and that call no function of the clock; caching plans across changing literals (parameterised plans) was evaluated and not built: planning is 0.1–0.3 ms, and substituting values into an optimised plan would lose the exact time filters. A SQL-free API for fixed questions (latest price, last N trades) was also left out: with the plan cache and reverse scans those answer in 0.1–0.3 ms through SQL.
- Replication is asynchronous with manual failover: a quorum-replicated log was evaluated (durable write 0.87 ms on the VM disk, 0.09 ms network round trip between two VMs) and left for later, because queries do not wait for durability and it is an availability feature, not a latency one.
- Arm build flags were measured on Neoverse V2 and are not used: inlined LSE atomics changed nothing; `-C target-cpu=neoverse-v2` gained about 1 % on ingest and up to 7 % on one query, not enough to ship a binary that only runs on that CPU generation.
- At 128-bit vectors (every mainstream cloud Arm CPU today) SVE2 is faster than NEON for the filters, gathers and 64-bit integer min/max, which run on SVE2; the sums, float min/max and counts stay on NEON, where SVE2 is 6 % to 2× slower (`docs/benchmarks/2026-11-13-axion-sve2-loop-shape.md`). Speed at SVE2 widths above 128 bits is unmeasured: no such hardware can be rented. In the second comparison run QuestDB once returned a `sum` that was off by 12 × 2^32; it never reproduced and is unexplained.
- Recovery speed (F-19) is measured on the laptop only (see `docs/benchmarks/`); the 10 GB / 60 s target needs a server-class NVMe run. Start-up also rebuilds continuous queries by reading their input tables once per query: unmeasured on large histories.
- Delivery guarantees: file and Kafka sources are at least once (a crash repeats about one second of messages; the per-partition ordering rule rejects repeated older rows but not a repeat of the newest timestamp); NATS core is at most once. No exactly-once, no Kafka consumer groups (positions are kept per partition in `sources.json`, by design), no NATS TLS or credentials files. Kafka has TLS and SASL `PLAIN` / `SCRAM-SHA-256/512`; `OAUTHBEARER`, Kerberos and MSK IAM are not available, a session the broker expires (KIP-368) is handled by reconnecting, and the managed services (Confluent Cloud, MSK, Aiven, Redpanda Cloud) have not been tested with live accounts.
- Ingest is bounded by what the WAL volume makes durable: a real-time feed that outruns the disk drops frames at the source channel (counted). A frame the log does not take within 2 s (stalled or failing disk) is dropped, not ingested (`ankaa_wal_dropped_total`); if it was a message of a user source the server stops (exit code non-zero, systemd restarts it) so that file and Kafka sources read it again. NATS messages lost that way are lost.
- With synchronised order books the WAL is kept back to the last feed connection before the checkpoint; when it outgrows `storage.wal_budget_mib` the books are re-based on fresh REST snapshots (at most every 10 minutes), which gives the log a new starting point at the price of a short gap in `quotes` while the snapshots arrive. Recovery replays the log from that point. Books run with `feed.depth_snapshots = false` are not replay-exact: `quotes` regenerated after a crash can differ from the originals.
- A WAL record that straddles a chunk boundary and contained a row the table rejected can have one row applied twice on crash recovery (never lost).
- Dictionary lookups use foldhash with a random seed per dictionary: fast, and resistant to aimed collisions only in the minimal sense (not a cryptographic hash); dictionary sizes are bounded by `max_dict_entries`.
- No cap on the number of Flight connections (each is limited to 64 concurrent calls; queries are capped globally).
- Replication is asynchronous with manual failover; there is no fencing of an old primary (the WAL `epoch` field is constant) and no automatic re-seed.
- Keyed ASOF continuous queries are limited to the market tables (user tables keep one dictionary each). Continuous queries drop late rows (no retraction).
- User tables can gain nullable columns at the end (or make a column nullable) with their history kept; any other column change stops the start with the reason (restore the definition or move the segments away).
- The `file://` capture feed re-serves its captures on every start: do not combine it with `storage.wal_dir` outside demos.
- Postgres wire: no TLS of its own and no statement timeout (the query memory pool applies); trusted tools only. `/metrics` is plaintext.
- Replay inputs are operator-supplied and partly trusted: WAL segments are read whole into memory at recovery (bounded by the 256 MiB segment size), CSV and Parquet files are read as they are.
- Not yet fuzzed: CSV/Parquet replay sources, segment metadata, the `/metrics` request parser; `capture_decode`/`wal_replay` are CRC-gated (structure-aware variants planned).
- `asof_join`/`ohlcv`/`percentiles` table functions collect both inputs in memory (bounded by the query memory pool, not streaming yet).
- Flight SQL: no statement parameters (a statement with `$1` or `?` is refused, so `PreparedStatement.setX` in JDBC and bound parameters in ADBC do not work; values go in the SQL text), no key or type-info metadata, no `CancelQuery`. The JDBC driver has not been run against the server: what it sends at connect (a `Handshake` with a bearer or Basic header) is covered by tests, its metadata calls beyond the supported ones are not. The command dispatch has no fuzz target yet.
- MQTT ingest costs about 10 µs of server CPU per message on Axion, three quarters of it in the MQTT client (rumqttc writes every acknowledgement on its own); the engine's share is about 2.5 µs. Batching readings per message (`rows`, Sparkplug) brings it to about 1.1–1.3 µs per reading.
- `ankaa-wire` has no AF_XDP path and no bare-metal numbers.
- Segments carry no per-file checksum beyond the Vortex layout (metadata row count is checked).

## Facts worth keeping
- `libc` does not export `HWCAP2_SVE2`; it is bit 1 of `AT_HWCAP2` (kernel UAPI).
- Disassemblers print SVE branch aliases as flags (`b.first` = `b.mi`, `b.none` = `b.eq`); the branchless gate checks the predecessor instruction.
- dm-flakey has no message interface and `drop_writes` makes writes *succeed* without reaching the device: freeze the writer before the table reload or a rig acknowledges phantom commits.
- Binance diff-depth messages must be applied atomically before sampling top of book.
- Apple M4 exposes SME2 (512-bit streaming SVE) but no SVE outside streaming mode; build with `+sme2` and without base SVE or the compiler emits `addvl` that faults.

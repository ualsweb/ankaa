# Security

ANKAA ingests untrusted network data and exposes a query interface. This page states the threat model,
what is implemented today, and what is planned. Report vulnerabilities as described in `SECURITY.md`.

## Attack surface and mitigations

| Surface | Risk | Today | Planned |
|---|---|---|---|
| Feed frames (WebSocket JSON, Binance SBE, Databento DBN, user-defined length-prefixed feeds) | malformed input → panic, memory exhaustion, wrong data | decoders return errors, never index blindly; fixed-point parser rejects overflow and precision loss; capture reader bounds frame length (16 MiB) and verifies CRC32C per frame; the generic framer bounds frame length and desynchronises explicitly; `cargo-fuzz` targets: `binance_json`, `binance_sbe`, `capture_decode`, `parse_fixed`, `wal_replay`, `dbn_replay`, `config_toml`, `framing`, `generic_map`, `sparkplug`, `line_protocol` (5 min each on PRs, nightly); `clippy::unwrap_used` denied in the library crates on the ingest path (`ankaa-ingest`, `ankaa-feeds`, `ankaa-wal`); fixture and property tests | fuzz targets for the CSV/Parquet sources and segment metadata; `panic = "abort"` in release with the systemd unit as supervisor (`deploy/systemd/`) |
| WAL and segment replay | corrupted or hostile files → wrong recovery | CRC32C per record, length bound, LSN sequence check; corruption stops replay with the offset; torn tail repaired only on the final segment; LSNs are never reused (the log restarts above everything segments and saved positions refer to); a segment that cannot be read or whose column set differs from its table stops the start instead of being skipped and later overwritten | replay in a sandboxed process with memory limits for untrusted files |
| Arrow Flight | unauthenticated access, SQL from clients | bearer token compared in constant time; binding to non-loopback addresses without a token is refused, and so is a Flight listener beyond loopback **without TLS** unless `server.allow_plaintext = true` (the token would travel in clear text); tokens must be at least 16 characters beyond loopback; **read-only SQL only**: DDL, DML and statements are rejected before planning (tested), so clients cannot create tables, touch the filesystem through external tables or `COPY`, or change session settings; **TLS** (rustls, `server.tls_cert`/`tls_key`) with optional **mutual TLS** (`server.tls_client_ca`), tested with generated certificates including wrong-name, wrong-CA, plaintext-to-TLS and missing-client-cert refusals | query timeouts and memory limits via DataFusion runtime config |
| Flight SQL (same listener and port as Arrow Flight; ADBC, JDBC) | a second command set on the query port: writes, state kept per client, malformed protobuf, a weaker way to authenticate | every call checks the bearer token before anything is decoded, `DoPut`, `DoAction` and `ListActions` included; `Handshake` is the one call that carries the credentials itself: it takes the token as a bearer header or as the password of `Basic` authentication (any user name; this is what ADBC and the JDBC driver send when given a user name and a password), compares it in constant time, counts refusals in `ankaa_query_unauthenticated_total` and answers with `authorization: Bearer <token>`, which is the secret the client has just shown; no other token is issued and nothing is stored. `Basic` is accepted on `Handshake` only and needs TLS like the bearer header does; statements go through the planning and execution functions of plain Flight, so the read-only check, the query timeout, `server.max_concurrent_queries` and the memory pool are the same (tested on this path); catalog metadata (`GetCatalogs`, `GetDbSchemas`, `GetTables`, `GetTableTypes`, `GetSqlInfo`) is answered from the catalog inside the query timeout, without a query slot, like `ListFlights`; statement tickets and prepared-statement handles are the SQL text: the server keeps nothing per client and a forged handle is an ordinary query; updates, bulk ingest, transactions, Substrait plans and statement parameters are refused with a status, and `DoPut` reads one message (at most 4 MiB, inside the query timeout) and writes nothing; commands are decoded with prost and answered with a status when malformed, with no `unwrap` or indexing on client input (tested with broken envelopes, hostile filter patterns and 200 seeds of random bytes on every call that decodes) | a fuzz target for the command dispatch; statement parameters |
| PostgreSQL wire (`server.pg_addr`, experimental, off by default) | writes through a second interface, shared-session changes, weak auth | SCRAM-SHA-256 with the token as password, a random salt per process, per-connection handshake state; a hook that runs before every other handler checks the statement type **and** the planned `LogicalPlan` with the same DataFusion `SQLOptions` gate as Flight (DDL, DML, `COPY`, `SELECT … INTO`, `EXPLAIN ANALYZE <write>`, cursors and `SET datafusion.*` are refused; a short allowlist of client-compatibility `SET` variables is accepted: the ones kept per connection go to the compatibility hook, every other form (`SET timezone = …`, `SET SESSION …`) is acknowledged and dropped, so nothing reaches the session all clients share; a statement that fails to plan in the gate is refused, not passed on; `WITH … INSERT` bodies are refused; transaction control and connection housekeeping (`BEGIN`, `COMMIT`, `ROLLBACK`, `SET TRANSACTION`, `SET NAMES`, `DISCARD ALL`, `DEALLOCATE`) are accepted because drivers send them, and change nothing); tested with a real Postgres client incl. a file-write canary | TLS on the pg listener (today: loopback or a TLS terminator) |
| `/metrics` | information leak, scrape DoS, credential reuse | loopback by default, exact `Authorization: Bearer` header parse with constant-time compare, one request per connection, one 5 s deadline for the whole exchange, at most 32 connections served at once; optional separate token (`server.metrics_token_env`) so a scrape path never carries the SQL credential (default: the Flight token; no TLS on this endpoint) | rate limit |
| Generic sources (MQTT, NATS, Kafka, files) | hostile messages on a subject/topic; unbounded keys; replay or loss across restarts | messages are size-limited (`max_message_bytes`, default 1 MiB, larger ones dropped and counted), JSON nesting is limited to 128 levels and a message to 65,536 rows (`rows`), new dictionary values of one message count against `max_dict_entries` together, parsed with the fixed-point parser and a JSON parser, mapped row by row, rejected (and counted) on any mismatch; dictionary columns are capped (`max_dict_entries`, 256-byte values, no objects/arrays as keys), so a producer cannot create partitions without bound; timestamps more than a day ahead are refused; source ids are 16-bit, checked and stable; file and Kafka positions are saved only once the data before them is durable; credentials in a NATS or MQTT URL are never logged; MQTT (`mqtts://`) and Kafka (`tls = true`) connect with TLS 1.3/1.2 (rustls, aws-lc-rs), the broker certificate checked against the public roots or only a private CA (`tls_ca`), with an optional client certificate (`tls_cert`, `tls_key`), and the files are checked before the start; Kafka authenticates with SASL `PLAIN` or `SCRAM-SHA-256/512`, the password taken from an environment variable (`sasl_password_env`), never logged, printed or serialized; SASL without TLS is refused unless the broker is on loopback or the source sets `allow_plaintext = true` (a warning at every start); an MQTT message is acknowledged only after it is in the ingest channel; Sparkplug B payloads are decoded in place with bounds on every length (65,536 metrics per message, 1,000,000 BIRTH definitions per source, 1 KiB names), checked against a reference protobuf codec (property test) and fuzzed (`sparkplug`); InfluxDB line protocol is read in place with every index checked (65,536 lines per message, 4,096 tags plus fields per line, a malformed or non-UTF-8 line refused alone), checked line by line against the parser of InfluxDB 3 on generated and damaged input (property test) and fuzzed (`line_protocol`); the only thing the server ever publishes is the opt-in Sparkplug rebirth request (`sparkplug_rebirth`, QoS 0, at most once per 30 s per node); fuzzed (`generic_map`) | TLS for NATS (today: user/password in NATS URLs; use a trusted network or a local TLS proxy); Kafka `OAUTHBEARER`, Kerberos and IAM authentication and SASL re-authentication (today: user name and password mechanisms only; a broker that expires sessions makes the source reconnect); per-source rate limits |
| WAL streaming to standbys | reading the whole log remotely; memory or I/O exhaustion through many streams; a standby silently diverging | **off by default** (`replication.serve_wal`); a separate replication token (`replication.token_env`) so SQL clients cannot open the log (without it the query token is accepted and the server warns at start); at most `replication.max_standbys` streams (default 4); each poll reads only new bytes, bounded at 8 MiB; only durable records are served; a request for truncated records or from a longer log is refused with a distinct status and the standby stops instead of continuing with a gap | fencing of an old primary (epochs), per-client allowlist |
| Query resources | one query exhausting memory or CPU, or running forever; a client that stops reading; many queries at once | DataFusion memory pool bounded by `resources.query_memory_mib` (default 1 GiB) with spilling to disk disabled: an operator that needs more fails. The table functions (`ohlcv`, `asof_join`, `percentiles`) read their input when the query executes, charge it to the same pool and run on the blocking pool, so planning (`GetFlightInfo`, `EXPLAIN`) costs nothing and a call over too much data fails with "resources exhausted" (tested). The pool does not see every allocation a query can cause (large values built by string functions, protocol buffers): set `MemoryMax=` in the systemd unit as the outer limit. At most `server.max_concurrent_queries` (default 32) queries execute at once over Flight. Per-query wall-clock timeout `server.query_timeout_s` (default 30 s) covers planning and execution and is enforced by a task that owns the plan, so it also fires when the client has stopped reading (tested); HTTP/2 keepalive drops clients that vanished; each connection is limited to 64 concurrent calls. Listener tasks are watched and the process exits non-zero after an orderly shutdown (systemd restarts it) if one dies. The Postgres listener serves at most 64 connections and has **no statement timeout**: expose it to trusted tools only | a cap on Flight connections; statement timeout on the Postgres listener |
| Source connection | reconnect storms, memory growth under backpressure, credentials on the wire or in logs | exponential backoff capped at 60 s; bounded channel with drop-and-count for real-time sources (the reader never blocks); feed and broker URLs are logged without credentials or query strings; an exchange API key is refused over `ws://`; REST snapshot bodies are size-limited while they are read; stream names are restricted to letters, digits, `@` and `_` | per-source quotas |
| Configuration | hostile config file, unsafe defaults | TOML with `deny_unknown_fields`, range and consistency validation (non-loopback binds require a token; TLS cert/key together; Kafka SASL needs TLS beyond loopback and a password variable that is set; stream names; checked size arithmetic), fail-fast resource checks (`RLIMIT_MEMLOCK`, physical memory, TLS files of the server and of the sources, directories; `config check` is a dry run); secrets via environment variables (the `--token`/`--api-key` flags also exist for development and are visible in `ps`), tokens and SASL passwords redacted in `Debug` and absent from `to_toml`, broker URLs printed without credentials in `Debug`; fuzzed (`config_toml`) | — |
| Segments on disk (Vortex files) | tampered segment → wrong data | metadata row count checked against the file; unreadable files are skipped and counted; schema must match the table | per-segment checksums in metadata |
| Dependencies | supply chain | `cargo-deny` (advisories, licenses, bans, sources) in CI on every lockfile in the repository (workspace, Python package, fuzz, bench); GitHub Actions pinned to commit SHAs with read-only default permissions; exact pins for the two fast-moving 0.x data-plane crates (`vortex`, `datafusion-postgres`), committed lockfiles for everything else | reproducible builds, SBOM |

## Memory safety
`unsafe` is confined to `ankaa-simd` (NEON intrinsics and SVE2 assembly), `ankaa-ring` (SPSC slots), `ankaa-core`
(`getrlimit`/`sysconf` calls) and `ankaa-wire` (counter reads, `recvmsg` control messages). The ring and store run under
miri in CI; NEON intrinsics are outside miri's reach and, like the SVE2 assembly, are verified by differential tests
against the scalar reference (all ten kernels, SVE2 at three vector lengths under QEMU, branchless gate on every
kernel). All other crates have `#![forbid(unsafe_code)]`.

## Operational guidance
Run `ankaad serve` behind a private network or on loopback. Always set `ANKAA_TOKEN` when binding beyond loopback and
enable TLS (`docs/deployment.md`). Pass secrets through the environment (`ANKAA_TOKEN`, `server.token_env`,
`replication.token_env`, `feed.api_key_env`, a source's `sasl_password_env`): the `--token` and `--api-key` flags exist for development and are visible
to every local user in the process list. The Postgres listener and `/metrics` are plaintext: keep them on loopback or
behind a TLS terminator. Give the replication stream its own token. Connect Kafka sources with `tls = true` unless the broker is on the same host. Treat capture, DBN, CSV and Parquet files from untrusted sources as hostile input
(replay them in an isolated environment). The systemd unit in `deploy/systemd/` restarts the process on abort.
